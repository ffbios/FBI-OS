# FBI Digital HQ authentication setup

**Applies to:** `ffbios/FBI-OS` on the `ecosystem-foundation` branch  
**Production status:** Not deployed by this change  
**Last updated:** 2026-10-15

## What is implemented

- Server-verified sign-in using a server-managed user directory.
- Scrypt password hashes; no browser-side account creation or password storage.
- Random, opaque session cookies marked `HttpOnly`, `SameSite=Strict`, and `Secure` in hosted environments.
- Eight-hour sessions stored on the server process. Logging out revokes the session. Updating a user's password hash or role invalidates their existing sessions.
- Same-origin checks on login/logout, a CSRF token requirement for logout, and an in-memory limit of eight failed sign-in attempts per source address per 15 minutes.
- Server-enforced roles and permissions: `super_admin`, `administrator`, `manager`, and `viewer`.
- Audit events for sign-in success/failure, logout, and viewing service-health reports. Logs deliberately exclude passwords, cookies, CSRF tokens and upstream response bodies.
- A protected health endpoint at `/api/ecosystem/health`. Health checks use only the explicit HTTPS `healthUrl` entries in the registry and only allow `fbigh.com`, its subdomains, and Railway-generated `.up.railway.app` domains. Redirects are not followed.
- Cross-system invoice/file snapshots remain disabled. Their routes require an authenticated role that can read administrative summaries, then return HTTP 503 until their upstream API contract and data permissions are implemented.

## Required Railway configuration before deployment

Do not deploy the protected Admin Hub until its user directory is configured. Without a valid directory, login intentionally fails closed.

1. Open the **FBI Digital Platform** Railway project.
2. Select the **`fbi-gh-website`** service.
3. Open **Variables** in the target environment.
4. Generate a password hash using the repository's utility (see below).
5. Add `FBI_HQ_USERS_JSON` with a JSON array of authorised accounts, then deploy only through the approved release process.

### Generate a password hash

Run this locally from the repository root using Node.js 20 or newer:

```bash
node scripts/hash-password.js
```

The script asks for a password without echoing it in an interactive terminal. Use a unique password of at least 12 characters. It prints a scrypt hash; copy that hash to the environment variable configuration, **not into GitHub, chat, or this file**.

### Example user-directory structure

Use your own real email and the actual hash generated by the script. The value below is a shape example only and cannot authenticate:

```json
[
  {
    "email": "admin@example.com",
    "role": "super_admin",
    "passwordHash": "scrypt$16384$8$1$REPLACE_WITH_32_HEX_SALT$REPLACE_WITH_128_HEX_KEY"
  },
  {
    "email": "manager@example.com",
    "role": "manager",
    "passwordHash": "scrypt$16384$8$1$REPLACE_WITH_32_HEX_SALT$REPLACE_WITH_128_HEX_KEY"
  },
  {
    "email": "viewer@example.com",
    "role": "viewer",
    "passwordHash": "scrypt$16384$8$1$REPLACE_WITH_32_HEX_SALT$REPLACE_WITH_128_HEX_KEY"
  }
]
```

Each configured hash must be created separately. The scrypt salt is random, so identical passwords should not have identical hashes. Email addresses are normalised to lowercase. Duplicate emails, unknown roles, malformed JSON, and invalid hashes make the entire directory invalid and sign-in unavailable.

Supported roles:

| Role key | Display name | Current permission intent |
|---|---|---|
| `super_admin` | Super Administrator | All defined permissions, including future account administration |
| `administrator` | Administrator | Read/write administrative permissions, but not user management |
| `manager` | Manager | Read-only operational/admin summaries |
| `viewer` | Read-Only Viewer | System directory and service-health reporting only |

Role definitions are server-side. The current implementation does not provide an account-management screen. Add/change/disable accounts by updating the protected Railway environment variable and redeploying through the approved release process. Updating a role or password hash invalidates existing sessions for that account.

## Session and scaling limitations

The current session store and login rate limiter are in process memory. This is suitable only for the current single-replica Admin Hub baseline:

- A service restart or deployment signs everyone out.
- Before running more than one replica, replace the in-memory session and rate-limit stores with a shared, protected store such as a properly configured PostgreSQL or Redis service.
- Do not point the Admin Hub at the crashed legacy `FBI Admin Postgres` service without first diagnosing it and confirming its data and recovery plan.
- Do not log or inspect environment-variable secret values in routine diagnostics.

## Runtime verification after an approved deployment

1. Visit `/admin`; unauthenticated access should show only the sign-in screen.
2. Confirm an invalid password receives a generic error and no session cookie.
3. Sign in with the configured Super Administrator account; verify the role and system-health page appear.
4. Call `/api/auth/me` without a cookie and confirm HTTP 401.
5. Call `/api/ecosystem/health` without a session and confirm HTTP 401.
6. Verify a read-only Viewer receives HTTP 403 from `/api/admin/invoice-snapshot` and `/api/admin/files-snapshot`.
7. Verify logout requires the returned CSRF token and revokes the session.
8. Test from desktop and mobile, and verify all Unknown health checks are clearly labelled.
9. Keep invoice/file summary proxies disabled until their downstream APIs are authenticated, scoped and tested end to end.

## Security boundary

The directory and health endpoints are part of the FBI-OS service. This does **not** establish single sign-on for Invoice Studio, Client File Studio, FBI Live, the IT Command Center, or the staff portal. Each application must continue enforcing its own access controls. Do not treat opening an application from Digital HQ as permission to access it.
